# Storyline Studio

Open `/command#stories` with an active league administrator account. The existing Command Center admin restriction and database RLS both apply.

1. Select an official game and click **Prepare Next Game**. The unique game constraint prevents duplicate workspaces.
2. Enter the producer, campaign objective, audience target and event link. Select one main story and up to two supporting stories, with verified evidence.
3. Assign the seven production beats. Deadlines are offsets from the live official fixture; interrupted fixtures block recording new releases. Short-turnaround beats can be skipped with a reason.
4. Attach final asset links and complete release checks. Save approval before marking released. Release is a record of an external publishing action, not a publishing integration. The server stamps reviewer/time; editorial changes reopen review.
5. Complete the show rundown, personnel, cue timing and backups. Record episode talent profiles and permissions.
6. After the result, use the relevant outcome branch. Record campaign metrics with their source/reporting period and one experiment for the next game. Gate attendance is read from Game Revenue and is not claimed as campaign attribution.

All workspace changes require explicit Save. Optimistic revision checks prevent silent overwrites; conflict recovery offers a downloadable JSON production packet before Reload latest. The audit trail contains before/after documents. No competition records are changed. Existing creative notes remain visible beneath the Studio.

## Boundaries

The first release provides deterministic templates, verified fixture/prior-meeting suggestions, shared persistence, task status, in-app overdue alerts, approval controls, rundown, episode talent cards and evidence-based impact review. It does not send employee notifications, upload media, publish to social platforms/RCH TV, automatically collect campaign analytics, or infer franchise valuation. Asset URLs point to existing media. Talent cards are episode-specific. Producers must review sources and permissions.

## Verification

Unit coverage exercises deadlines, interrupted/final results, evidence-based suggestions, release prerequisites, skipped-work reasons, unknown metrics, and campaign links. Database verification runs rollback-only admin/nonadmin access, optimistic-revision and release-gate tests against the matching project; no test production records are retained.
